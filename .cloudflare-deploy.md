# Cloudflare — deployment settings

The site is deployed by **Cloudflare Workers Builds**, not Cloudflare Pages.
That distinction is not cosmetic: the two products set different environment
variables, and the preview-noindex guard was written against the Pages one and
therefore did nothing until 2026-08-04. See *Branch detection* below.

Live: <https://swiftsecured.com>
Worker name: `swift-secure` — created before the Swift Secure → Swift Secured
rename, so it is missing the "d" that `package.json` has. `wrangler.jsonc`
matches the Worker, deliberately.

`swift-secure.muzexp.workers.dev` is deliberately off; see `workers_dev` in
`wrangler.jsonc`.

Most of the build behaviour now lives in `wrangler.jsonc`, which is committed
and read by `wrangler deploy`. Only the table below is entered by hand in the
dashboard.

## Build configuration

| Field | Value |
| :--- | :--- |
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy --env=""` |
| Non-production branch deploy command | `npx wrangler versions upload` |
| Root directory | *(leave empty)* |
| Node version | `24` — set as env var `NODE_VERSION` |

Both deploy commands must be set by hand, in **Settings → Build → Build
configuration** (the pencil). They are the only part of this setup that cannot
live in the repository, which is why they are the only part that has broken the
live site.

> **This has already gone wrong once, on 2026-08-04.** The second field shipped
> as `npx wrangler deploy` instead of the documented default
> `npx wrangler versions upload`. So the first push to the `staging` branch did
> not create a preview — it deployed over production. For about six minutes
> swiftsecured.com served the staging build: the orange STAGING bar on every
> page, noindex on every page, and `robots.txt` returning `Disallow: /`. Nothing
> in the repository was wrong; an empty commit to `main` rebuilt and restored it.
>
> The lesson is not "check the dashboard". It is that a preview branch is only
> a preview because of one text field nobody looks at, and the failure is
> invisible from the repository — the branch deploys, the build goes green, and
> the only symptom is on the live site.

`--env=""` is not decoration. Once `wrangler.jsonc` defines any environment, a
bare `wrangler deploy` becomes ambiguous and wrangler says so on every build. It
still targets the top-level environment today, so production is correct by
accident rather than by instruction. The empty string says top-level, out loud.

**Wrangler is pinned to an exact version in `devDependencies`.** Until 5 August
2026 it was not installed at all, so `npx wrangler` downloaded whatever was
newest at the moment each build ran — four releases went out in the eleven days
before the pin. Every deploy was therefore made by a tool nobody had chosen.

The pin is `"wrangler": "4.120.0"` with **no caret**. `npm i -D wrangler@4.120.0`
writes `^4.120.0`, which permits any 4.x and pins nothing; `--save-exact` is what
makes it a version rather than a range.

### Touch package.json only with the npm version the builder uses

**Cloudflare builds with npm 10.9.2. This PC has npm 11.6.1, and they disagree
about the lockfile.**

The build runs `npm clean-install` before anything else. Installing wrangler on
10 August rewrote part of the tree with the local npm, and npm 10.9.2 then
refused the result:

```
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json are in sync.
npm error Missing: @emnapi/runtime@1.11.3 from lock file
```

Five pushes to `staging` failed at 14 seconds each, before `npm run build` ever
ran. Nothing about the copy was wrong; the site simply never rebuilt, and
staging went on serving a three-day-old deployment while every push looked
delivered from this end.

The disagreement is over hoisted transitive packages under the WASM fallbacks of
rolldown, satteri and tailwindcss/oxide. Local npm nests `@emnapi/*` and writes
1.11.1; npm 10.9.2 wants 1.11.3 at the top level.

So, after anything that writes to `package-lock.json`:

```bash
npx npm@10.9.2 install --package-lock-only   # rebuild the lock the way CI will read it
npx npm@10.9.2 ci --dry-run                  # this is the command that actually failed
```

**`npm ci --dry-run` with the local npm proves nothing.** It passed while the
build was broken, because the local npm was validating a lockfile it had written
itself.

For the pin to reach the build, Cloudflare has to install devDependencies. It
does by default, but if a build log ever shows a different version, the fallback
is to name it in the deploy command itself — `npx wrangler@4.120.0 deploy …` —
and not to give up on pinning.

The non-production command sends **every** branch that is not `main` to
`staging.swiftsecured.com`. Two branches in flight at once will overwrite each
other there; last push wins. Left at its default it would instead be
`npx wrangler versions upload`, which is safe but hands back a different URL
containing a version id on every push — no use for a link you want to send twice.

There is no "build output directory" field to set: `wrangler.jsonc` points at
`./dist` itself.

**Do not remove `wrangler.jsonc`.** With no config file, `wrangler deploy`
treats the repo as an unconfigured Astro project and runs `astro add cloudflare`
on the build machine — installing an SSR adapter it warns is untested against
this Astro version, and building all 4,428 pages a second time. The site is
static and needs neither.

## Branch detection

Workers Builds sets **`WORKERS_CI_BRANCH`**. Pages set `CF_PAGES_BRANCH`. Both
are read in `src/lib/deploy.ts`; a build with neither (local, GitHub Actions) is
treated as production, which is correct for both.

| Branch | Deploys to | Indexed by search engines |
| :--- | :--- | :--- |
| `main` | `swiftsecured.com`, `www.swiftsecured.com` | Yes |
| anything else | a per-version preview URL | **No** |

Set `main` as the production branch under **Settings → Build → Branch control**.

`staging.swiftsecured.com` is not a setting inside this project and cannot be
made into one. It belongs to a second Workers project — see *The staging
project* below.

> **Why, and what it cost.** The obvious approach — an `env.staging` block in
> `wrangler.jsonc` and `npx wrangler deploy --env staging` for non-production
> branches — took the live site down on 2026-08-04. Workers Builds is bound to
> one Worker and overrides the name the config asks for; it says so in the very
> first line of every build log. So `--env staging` did not create a second
> Worker. It redeployed *this* one with staging's routes instead of
> production's, detaching `swiftsecured.com` and `www` and deleting their DNS
> records. The site answered Cloudflare error 1016 for about four minutes, until
> the next production deploy restored them — and deleted staging's in the same
> move. Two environments, one Worker, last deploy wins.
>
> `wrangler deploy --env staging --dry-run` passed cleanly beforehand. It cannot
> catch this: the configuration is valid, and the damage comes from the CI
> renaming the target afterwards.
>
> Removing the `env` block does **not** make the command safe. Wrangler warns
> that the environment does not exist and then deploys the top-level config
> anyway — so a staging push would put the staging build, banner and all, on the
> live domain. The dashboard field is the only control that matters.

## The staging project

A second, separate Workers project — `swift-secure-staging` — connected to the
same repository, with `staging` as *its* production branch. A different Worker,
not a second environment inside this one.

| Field | Value |
| :--- | :--- |
| Production branch | `staging` |
| Branch control | include **`staging` only** |
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy --config wrangler.staging.jsonc --env=""` |
| Non-production deploy command | `npx wrangler versions upload --config wrangler.staging.jsonc --env=""` |

Variables: `NOINDEX_DEPLOY=1`, plus `NODE_VERSION`, `PUBLIC_CONTACT_EMAIL` and
`PUBLIC_FORM_ENDPOINT` copied from production. **No `SITE`** — `astro.config.mjs`
already defaults to `https://swiftsecured.com`, so staging canonicalises to the
real site instead of claiming to be the original.

`--config` is the whole safety mechanism. Without it the command reads
`wrangler.jsonc`, which names the production hostnames, and CI has no terminal
to ask — wrangler reassigns them and the build stays green. If a staging build
ever fails with *could not read file*, the fix is to commit the config to that
branch. **It is never to drop `--config`.**

`NOINDEX_DEPLOY=1` is belt and braces. The branch check already covers it, but
if the staging project were ever pointed at `main`, the branch check would call
that build production and publish an indexable second copy.

**Builds for non-production branches: disabled.** Left on, every push to `main`
would also build here. That is not dangerous — the non-production command is
`versions upload`, which uploads a version without deploying it and never
touches a custom domain — but it builds 4,428 pages a second time for nothing,
and it fills this Worker's version list with `main` builds that somebody could
one day promote by mistake. `preview_urls` is off, so those builds do not even
produce an address anyone can open.

The production project must also be limited to **`main` only** under branch
control. Otherwise every push to `staging` runs `versions upload` against the
production Worker, filling its rollback list with builds that carry the STAGING
banner and `Disallow: /` — one click from being promoted on the day someone
needs to roll back in a hurry.

### Never merge the pull request Cloudflare offers

On connecting the repository, the dashboard shows:

> Update `wrangler.jsonc` in your repo to keep settings consistent. On Wrangler
> v3.109.0+, we will auto-generate a PR to fix this after the build.
> `"name": "swift-secure-staging",`

Close it. There is nothing inconsistent to fix.

The dashboard compares the Worker's name against the *default* config file name.
It cannot see `--config wrangler.staging.jsonc` in the deploy command, because
to it that is an opaque shell string. So it reports a mismatch that does not
exist: the config this project actually reads already says
`swift-secure-staging`.

Merging it would set `"name": "swift-secure-staging"` in `wrangler.jsonc` while
that file still lists `swiftsecured.com` and `www.swiftsecured.com` as custom
domains. Any later `npx wrangler deploy` with no flags — the obvious thing to
type on a laptop — would then deploy to the staging Worker *and move both live
domains onto it*. The same outage as 2026-08-04, arriving as a green pull
request titled "keep settings consistent".

## Environment variables

Set under **Settings → Variables and Secrets**.

| Name | Value | Notes |
| :--- | :--- | :--- |
| `NODE_VERSION` | `24` | Matches local development |
| `SITE` | `https://swiftsecured.com` | Production only. Astro uses it for canonical URLs |
| `PUBLIC_CONTACT_EMAIL` | the real inbox | Without it the apply form tells applicants it failed |
| `PUBLIC_FORM_ENDPOINT` | form-to-email endpoint | Optional; the contact address alone makes the page usable |

`WORKERS_CI_BRANCH` is set by Cloudflare itself. Do not add it manually.

## How previews are kept out of the search index

Two independent layers, because one of them silently failing is exactly the kind
of thing nobody notices until the duplicate pages are already indexed — and one
of them *was* silently failing, for the whole first day:

1. `src/layouts/Layout.astro` emits `<meta name="robots" content="noindex,
   follow">` on every page of a non-production build.
2. `src/pages/robots.txt.ts` serves `Disallow: /` on those same builds.

Canonical URLs keep pointing at `swiftsecured.com` even on a preview, so a
crawler that ignores both still learns where the real page is.

Verified by building with the branch variable set to `staging`: all 4,428 pages
carried the noindex tag and robots.txt switched to `Disallow: /`. A build
without the variable produced neither.
