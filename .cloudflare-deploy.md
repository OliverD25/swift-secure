# Cloudflare — deployment settings

The site is deployed by **Cloudflare Workers Builds**, not Cloudflare Pages.
That distinction is not cosmetic: the two products set different environment
variables, and the preview-noindex guard was written against the Pages one and
therefore did nothing until 2026-08-04. See *Branch detection* below.

Live: <https://swift-secure.muzexp.workers.dev>
Worker name: `swift-secure` — created before the Swift Secure → Swift Secured
rename, so it is missing the "d" that `package.json` has. `wrangler.jsonc`
matches the Worker, deliberately.

Most of the build behaviour now lives in `wrangler.jsonc`, which is committed
and read by `wrangler deploy`. Only the table below is entered by hand in the
dashboard.

## Build configuration

| Field | Value |
| :--- | :--- |
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy --env=""` |
| Non-production branch deploy command | `npx wrangler versions upload` |
| Root directory | *(leave empty)* |
| Node version | `24` — set as env var `NODE_VERSION` |

Both deploy commands must be set by hand, in **Settings → Build → Build
configuration** (the pencil). They are the only part of this setup that cannot
live in the repository, which is why they are the only part that has broken the
live site.

> **This has already gone wrong once, on 2026-08-04.** The second field shipped
> as `npx wrangler deploy` instead of the documented default
> `npx wrangler versions upload`. So the first push to the `staging` branch did
> not create a preview — it deployed over production. For about six minutes
> swiftsecured.com served the staging build: the orange STAGING bar on every
> page, noindex on every page, and `robots.txt` returning `Disallow: /`. Nothing
> in the repository was wrong; an empty commit to `main` rebuilt and restored it.
>
> The lesson is not "check the dashboard". It is that a preview branch is only
> a preview because of one text field nobody looks at, and the failure is
> invisible from the repository — the branch deploys, the build goes green, and
> the only symptom is on the live site.

`--env=""` is not decoration. Once `wrangler.jsonc` defines any environment, a
bare `wrangler deploy` becomes ambiguous and wrangler says so on every build. It
still targets the top-level environment today, so production is correct by
accident rather than by instruction — and an unpinned `npx wrangler` is free to
change that in a future major. The empty string says top-level, out loud.

The non-production command sends **every** branch that is not `main` to
`staging.swiftsecured.com`. Two branches in flight at once will overwrite each
other there; last push wins. Left at its default it would instead be
`npx wrangler versions upload`, which is safe but hands back a different URL
containing a version id on every push — no use for a link you want to send twice.

There is no "build output directory" field to set: `wrangler.jsonc` points at
`./dist` itself.

**Do not remove `wrangler.jsonc`.** With no config file, `wrangler deploy`
treats the repo as an unconfigured Astro project and runs `astro add cloudflare`
on the build machine — installing an SSR adapter it warns is untested against
this Astro version, and building all 4,428 pages a second time. The site is
static and needs neither.

## Branch detection

Workers Builds sets **`WORKERS_CI_BRANCH`**. Pages set `CF_PAGES_BRANCH`. Both
are read in `src/lib/deploy.ts`; a build with neither (local, GitHub Actions) is
treated as production, which is correct for both.

| Branch | Deploys to | Indexed by search engines |
| :--- | :--- | :--- |
| `main` | `swiftsecured.com`, `www.swiftsecured.com` | Yes |
| anything else | a per-version preview URL | **No** |

Set `main` as the production branch under **Settings → Build → Branch control**.

There is no `staging.swiftsecured.com`, and getting one is not a config change.

> **Why, and what it cost.** The obvious approach — an `env.staging` block in
> `wrangler.jsonc` and `npx wrangler deploy --env staging` for non-production
> branches — took the live site down on 2026-08-04. Workers Builds is bound to
> one Worker and overrides the name the config asks for; it says so in the very
> first line of every build log. So `--env staging` did not create a second
> Worker. It redeployed *this* one with staging's routes instead of
> production's, detaching `swiftsecured.com` and `www` and deleting their DNS
> records. The site answered Cloudflare error 1016 for about four minutes, until
> the next production deploy restored them — and deleted staging's in the same
> move. Two environments, one Worker, last deploy wins.
>
> `wrangler deploy --env staging --dry-run` passed cleanly beforehand. It cannot
> catch this: the configuration is valid, and the damage comes from the CI
> renaming the target afterwards.
>
> Removing the `env` block does **not** make the command safe. Wrangler warns
> that the environment does not exist and then deploys the top-level config
> anyway — so a staging push would put the staging build, banner and all, on the
> live domain. The dashboard field is the only control that matters.

**A real staging hostname needs a second Workers project**, connected to the same
repository with `staging` as *its* production branch and `staging.swiftsecured.com`
as its custom domain. A separate Worker, not a second environment inside this
one. Nothing in this repository has to change for that; the branch already
carries the STAGING banner and the noindex, keyed off `WORKERS_CI_BRANCH`.

## Environment variables

Set under **Settings → Variables and Secrets**.

| Name | Value | Notes |
| :--- | :--- | :--- |
| `NODE_VERSION` | `24` | Matches local development |
| `SITE` | `https://swiftsecured.com` | Production only. Astro uses it for canonical URLs |
| `PUBLIC_CONTACT_EMAIL` | the real inbox | Without it the apply form tells applicants it failed |
| `PUBLIC_FORM_ENDPOINT` | form-to-email endpoint | Optional; the contact address alone makes the page usable |

`WORKERS_CI_BRANCH` is set by Cloudflare itself. Do not add it manually.

## How previews are kept out of the search index

Two independent layers, because one of them silently failing is exactly the kind
of thing nobody notices until the duplicate pages are already indexed — and one
of them *was* silently failing, for the whole first day:

1. `src/layouts/Layout.astro` emits `<meta name="robots" content="noindex,
   follow">` on every page of a non-production build.
2. `src/pages/robots.txt.ts` serves `Disallow: /` on those same builds.

Canonical URLs keep pointing at `swiftsecured.com` even on a preview, so a
crawler that ignores both still learns where the real page is.

Verified by building with the branch variable set to `staging`: all 4,428 pages
carried the noindex tag and robots.txt switched to `Disallow: /`. A build
without the variable produced neither.
